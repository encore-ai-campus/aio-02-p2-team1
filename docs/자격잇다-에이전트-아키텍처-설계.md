# 자격잇다 — 에이전트 아키텍처 설계

현재 자격잇다의 기능과 개발 범위를 고려하면 LangGraph 기반 단일 에이전트 + 외부 도구(Tool) 구조로 구현하고, 추후 추천·검증·일정 관리 기능을 독립된 멀티에이전트로 분리하는 방향이 적합합니다.

핵심은 모든 기능을 LLM에 맡기지 않고, LLM이 판단해야 하는 부분과 일반 코드로 처리할 부분을 분리하는 것입니다.

## 1. 현재 권장 아키텍처 — 단일 에이전트

### 전체 시스템 구조도
```rust
flowchart TD
    user["사용자 · React"] --> backend["FastAPI Backend"]
    backend --> auth["인증 및 입력 검증"]
    auth --> route{"요청 유형"}
    route -->|조건 기반 추천| profile
    route -->|자격증 검색·상세| lookup["자격증 조회 서비스"]
    route -->|일정 등록| calendar["Calendar 서비스"]
    route -->|관심 목록| db[("PostgreSQL / Supabase")]
    subgraph recommendation["LangGraph 단일 추천 에이전트"]
        profile["사용자 조건 로드"] --> candidates["자격증 후보 조회"]
        candidates --> llm["LLM 관련성 평가"]
        llm --> verify["추천 결과 검증"]
        verify --> result["TOP 3 및 추천 이유"]
    end
    profile --> db
    candidates --> db
    lookup --> db
    lookup --> qnet["Q-Net 공공 API"]
    calendar --> dates["선택 회차·날짜 검증"]
    dates --> qnet
    dates --> google["Google Calendar API"]
    result --> user

```

Google 로그인은 별도 인증 계층에서 처리하며, 추천 에이전트와 Calendar 등록 서비스는 분리합니다.

### LangGraph 내부 실행 흐름
```rust
flowchart TD
    start(["START"]) --> input["사용자 조건 확인"]
    input --> required{"필수 입력 충족?"}
    required -->|아니요| missing["누락 항목 반환"]
    missing --> finish(["END"])
    required -->|예| search["DB 자격증 후보 검색"]
    search --> exists{"후보 존재?"}
    exists -->|아니요| empty["추천 후보 없음"]
    empty --> finish
    exists -->|예| recommend["LLM 후보 평가 및 추천 이유 생성"]
    recommend --> valid{"결과 검증 통과?"}
    valid -->|예| format["TOP 3 및 추가 후보 구성"]
    format --> finish
    valid -->|아니요·재시도 가능| retry["재시도 1회"]
    retry --> recommend
    valid -->|재시도 실패| fallback["규칙 기반 추천"]
    fallback --> format

```

이 구조에서 LLM은 DB에 존재하는 자격증 후보를 평가하고 추천 이유를 생성합니다. 추천 결과 검증, 중복 제거, 출력 개수 제한은 Python 코드로 수행합니다.

## 2. 단일 에이전트의 노드와 Tool 구성

| **구분** | **이름**                  | **담당 기능**            | **LLM** |
| ------ | ----------------------- | -------------------- | ------- |
| Node   | validate_input          | 관심 분야·학력·전공·경력 입력 검증 | X       |
| Tool   | get_user_profile        | 저장된 사용자 조건 조회        | X       |
| Tool   | search_certificates     | 조건에 해당하는 자격증 후보 조회   | X       |
| Node   | recommend_certificates  | 후보 관련성 평가 및 추천 이유 생성 | O       |
| Node   | validate_recommendation | 자격증 ID·중복·추천 개수 검증   | X       |
| Node   | format_result           | TOP 3 및 추가 추천 결과 구성  | X       |
| Node   | fallback_recommendation | LLM 실패 시 규칙 기반 후보 반환 | X       |

추천 결과는 예를 들어 다음과 같은 구조로 반환합니다.
```json
{
  "certificate_id": "CERT-001",
  "certificate_name": "일반기계기사",
  "reason": "기계 설계 분야에 관심이 있고 관련 전공을 보유한 사용자에게 관련성이 있습니다.",
  "related_jobs": [
    "기계설계",
    "생산기술"
  ]
}
```

여기서 `certificate_id`는 DB의 실제 식별자여야 하며, LLM이 새로 생성해서는 안 됩니다.

### Google Calendar 연동 구조

Calendar 등록은 이미 구현된 기능이므로 기존 코드를 유지하고, LangGraph의 추천 실행과 독립적으로 운영하는 것이 좋습니다.
```rust
flowchart TD
    select["시험 회차 선택"] --> qnet["Q-Net 일정 조회"]
    qnet --> validate["일정 데이터 검증"]
    validate --> request["사용자 등록 요청"]
    request --> calendar["Google Calendar API"]
    calendar --> result{"등록 결과"}
    result -->|성공| save["DB 이벤트 ID 저장"]
    result -->|실패| error["오류 반환·재시도"]

```

Google Calendar 등록을 반드시 LLM Tool Calling으로 수행할 필요는 없습니다. 현재처럼 명확한 버튼을 통해 등록하는 기능은 일반 API 호출이 더 예측 가능하고 테스트하기 쉽습니다.

## 3. 추후 멀티에이전트 확장 구조

향후 서비스 기능이 증가하면 Supervisor + 전문 에이전트 3개 구조를 추천합니다.
```rust
flowchart TD
    user["사용자"] --> api["FastAPI"]
    api --> supervisor["Supervisor · 요청 분류 및 작업조정"]
    supervisor --> recommendation["① 추천 에이전트"]
    supervisor --> eligibility["② 응시자격 검증 에이전트"]
    supervisor --> schedule["③ 일정 관리 에이전트"]
    recommendation --> search["자격증 DB 검색·LLM 추천"]
    eligibility --> criteria["응시자격 기준 조회·판정"]
    schedule --> calendar["Q-Net 일정 조회·Calendar Tool"]
    search --> result["결과 통합 및 검증"]
    criteria --> result
    calendar --> result
    result --> api

```

### 에이전트별 역할

#### ① 자격증 추천 에이전트 (Recommendation Agent)

관심 분야, 학력, 전공, 경력을 바탕으로 자격증 후보를 분석하고 TOP 3 및 추천 이유를 생성합니다. 현재 단일 에이전트의 기능을 그대로 분리할 수 있습니다.

#### ② 응시자격 검증 에이전트 (Eligibility Agent)

학력·전공·경력과 공식 응시자격 기준을 비교합니다. 판정 근거가 부족한 경우 '추가 확인 필요'를 반환하며, 공식적인 응시자격 확정 판정을 대체하지 않습니다.

#### ③ 일정 관리 에이전트 (Schedule Agent)

시험 회차 조회, 원서접수 기간·시험일 확인, Google Calendar 등록 요청을 처리합니다. 일정 생성·변경은 사용자 승인 후 기존 Calendar 서비스를 호출합니다.
